# Dependency Management and Verification

## Repository policy

Production and CI dependency resolution is centralized in `settings.gradle.kts` with
`FAIL_ON_PROJECT_REPOS`. The trusted repositories are:

- Google Maven (`google()`)
- Maven Central (`mavenCentral()`)
- Mozilla Maven, restricted by content filter to `org.mozilla.geckoview*`

`mavenLocal()` is intentionally absent. An unrestricted local Maven repository can shadow
official artifacts with matching coordinates. Development environments that genuinely need a
local artifact must add an explicitly content-filtered repository in a local, reviewed change;
such a change must not be merged into the production branch without documenting the artifact,
its exact coordinates, and why the official repositories cannot provide it.

## Version locking

`build.gradle.kts` enables dependency locking for all project configurations. `app/gradle.lockfile`
is committed and covers debug, release, devRelease, unit-test, androidTest, KSP and lint
configurations used by CI.

To intentionally update a dependency:

1. Change the version in `app/build.gradle.kts` or `.github/workflows/ci.yml`.
2. Run `.\gradlew.bat --write-locks testDebugUnitTest lintDebug lintRelease compileReleaseKotlin compileDebugAndroidTestKotlin assembleDebug assembleDebugAndroidTest assembleDevRelease`.
3. Review the dependency and lockfile diff, then commit directly to `main` (or review via temporary PR if desired).
4. Never hand-edit `app/gradle.lockfile`.

CI runs the locked graph and then verifies that the lockfile was not rewritten.

## Verification metadata

`gradle/verification-metadata.xml` records SHA-256 checksums for resolved artifacts and build
plugin dependencies. It was generated from dependencies resolved through the trusted repositories
after mavenLocal was removed; it is not generated from a local Maven repository. Verify metadata
is committed with the lockfile.

- Gradle verifies artifacts by default using this metadata.
- Module metadata (`POM`/`.module`) is not checksum-verified; binary artifacts (`.jar`, `.aar`,
  `.zip`) are. This keeps CI resolution independent of platform-specific metadata caches while
  still requiring SHA-256 agreement for every binary artifact.
- `verify-signatures` is disabled because checksum verification is the project baseline; PGP
  signatures are used for release manifests, not every third-party artifact.
- A failed verification is a build failure, not a warning.

Regenerate after a deliberate locked dependency update:

```bat
.\gradlew.bat --write-verification-metadata sha256 testDebugUnitTest lintDebug lintRelease compileReleaseKotlin compileDebugAndroidTestKotlin assembleDebug assembleDebugAndroidTest assembleDevRelease
```

Review the resulting metadata diff before committing. Do not blindly accept metadata produced by
a local Maven repository or an unreviewed cache.

## Automated monitoring

Automatic Dependabot version-update (`.github/dependabot.yml`) and security-update PR creation is
intentionally disabled so the repository retains a single permanent `main` development branch.
GitHub Dependabot vulnerability alerts remain enabled for maintainer triage and manual locked
updates on `main`. External pull requests still run GitHub dependency review.

## Limitations

- Checksum verification proves artifact integrity relative to the committed metadata, not the
  publisher's intent. Published metadata must be reviewed when dependencies change.
- The Mozilla repository is content-filtered, but other repositories rely on Gradle's normal
  HTTPS transport and Maven coordinate rules.
- No full SBOM is generated by this repository; dependency coordinates and lockfile are the
  authoritative inventory available in-tree.
