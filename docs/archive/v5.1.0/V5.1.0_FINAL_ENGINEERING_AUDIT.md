## 4. Long-Running Download Recovery (`cf4ca09`)

### 4.1 Why user-initiated data transfer jobs

Android 15 limits `dataSync` foreground services to six hours. A user-initiated data transfer (UIDT) job from API 34 is designed for transfers the user started: the system keeps the process alive for the duration, requires a visible notification, and is not subject to the six-hour dataSync window. UIDT is therefore used as a process-lifetime **anchor** on API 34+, while the existing foreground service remains the immediate-start mechanism and the fallback below API 34.

### 4.2 Architecture

- **Manager unchanged as executor.** `VrkaDownloadManager` still owns queuing, concurrency, yt-dlp execution, staging, publishing, and history.
- **One anchor job.** `DownloadTransferScheduler` keeps a single UIDT job (`id 4106`) scheduled while any job is foreground work, and cancels it when the queue is idle. Scheduling is idempotent (`getPendingJob` check), so concurrent jobs cannot create duplicate anchors. Scheduling failures are logged; the foreground service still runs.
- **Immediate start.** `DownloadService` is started as before at transfer start and on browser fallback, so transfers never wait for the job scheduler. Foreground-service start failures (for example background-start restrictions) are caught and logged; the transfer continues under the UIDT process anchor.
- **Six-hour handoff.** `onTimeout` now consults `DownloadRecovery.foregroundTimeoutAction`. When the transfer job is running, the service calls `stopForeground(STOP_FOREGROUND_DETACH)` and `stopSelf()` without removing notifications; the job service takes over progress and cancellation. Otherwise the previous interrupted-notification path is kept.
- **Notification ownership.** All notification content is centralized in `DownloadNotifications`, using the standard platform progress notification, per-job IDs (`4200+`), pending (`4107`), interrupted (`4108`), and completion records (`completed:<jobId>`, `100100`). The job service associates the primary notification with its own parameters via `setNotification(..., JOB_END_NOTIFICATION_POLICY_REMOVE)` and mirrors additional concurrent jobs with the same per-job IDs.
- **Concurrency.** The job service observes the manager's job flow, posts the first active job as the job-associated notification and the rest as ordinary notifications, cancels stale IDs, and finishes when no foreground work remains.

### 4.3 Persistence and recovery policy

- A `publishStarted` flag is written synchronously before any file leaves staging. It survives reloads and is reset only on explicit retry.
- `JobStore.load(recoverActive)` keeps in-flight states only when recovery is expected; otherwise in-flight records still become `FAILED` with the interrupted/retry message, as before.
- The job service marks its invocation in `DownloadTransferRuntime` before the manager reads persisted state, because `getPendingJob` is not a reliable signal while a job is running. Recovery therefore runs after persisted state is merged and only when a UIDT job is pending or was just invoked.
- Recovery decisions:

| Persisted state | Action |
|---|---|
| `QUEUED`, `PREPARING`, `DOWNLOADING`, `BROWSER_FALLBACK` | Resume (re-queue) |
| `POSTPROCESSING` before publish marker | Resume |
| `POSTPROCESSING` after publish marker | Fail closed — outputs may already exist |
| `WAITING_FOR_USER` | Leave waiting; never auto-start |
| `DONE`, `FAILED`, `CANCELLED` | Never restart |

- Stopping the app from Android's Task Manager cancels the job; the next launch has no pending job and therefore marks in-flight work interrupted instead of silently restarting it.
- Duplicate protection: one anchor job, one logical job record per download, the manager's existing `activeRunningJobs`/`pendingIds` guards, `yt-dlp --continue`/`--no-overwrites`, per-job staging directories, and the publish marker together prevent duplicate executions and duplicate published files.

### 4.4 Cancellation, network, staging, browser fallback

- Cancellation still flows from the notification action to `DownloadService.ACTION_CANCEL` and the manager; the job service finishes and removes its notifications when no foreground work remains.
- The job requires `NETWORK_TYPE_ANY`; the system may restart it after connectivity loss, and yt-dlp resumes fragments from staging.
- Staging stays under `externalFilesDir/staging/<jobId>`; publishing and cleanup are unchanged.
- Browser fallback starts the foreground service through the same safe path and is covered by the same anchor and recovery rules.

### 4.5 Files

- `DownloadTransferScheduler.kt` — job id, scheduling, runtime flags.
- `DownloadTransferJobService.kt` — UIDT worker, notification ownership, wake lock, idle finish.
- `DownloadNotifications.kt` — shared progress and completion notification builder.
- `DownloadRecovery.kt` — pure recovery and timeout policy.
- `DownloadService.kt` — timeout handoff and notification delegation.
- `JobStore.kt`, `DownloadModels.kt` — recovery load and publish marker.
- `VrkaDownloadManager.kt` — anchor scheduling, recovery application, publish marker.
- `AndroidManifest.xml` — `RUN_USER_INITIATED_JOBS` permission and unexported `BIND_JOB_SERVICE` worker.

### 4.6 Limitations

- No device verification was possible. The following need a hardware pass: six-hour handoff on Android 15+, process death with a running job, Task Manager stop, notification permission denied, concurrent jobs, and OEM-specific job throttling.
- If the platform refuses to schedule the anchor or the app cannot post the job notification, the architecture falls back to the existing foreground-service behaviour, including the interrupted notification at timeout.
- The UIDT job id is a fixed constant. A theoretical collision with a WorkManager-generated id would only delay one scheduler; both retry, and transfers fall back to the foreground service.
