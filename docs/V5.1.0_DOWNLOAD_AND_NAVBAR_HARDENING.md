## 3. Work Package 1 — Job Lifecycle and Automatic Retries (`01c39a9`)

Before this change, direct-extraction recovery was an ad-hoc check (`shouldRetryDirect`) with no attempt budget, no backoff, and no protection against callbacks from an older attempt overwriting a newer job state. The hardened pipeline:

1. **Single retry authority** — `engine/RetryPolicy.kt` decides retryability from the failure category, the error text, whether any bytes were transferred, and whether a media URL was already resolved.
2. **Bounded attempts** — at most `MAX_TOTAL_ATTEMPTS = 3` direct attempts (initial + 2 automatic retries). The loop in `VrkaDownloadManager` refuses to continue past the budget or once a cancellation is observed.
3. **Capped exponential backoff with jitter** — `BASE_DELAY_MS = 2,000`, doubling per retry, capped at `MAX_DELAY_MS = 20,000`, jittered by ±25 %. Jitter prevents several queued jobs from retrying in lockstep; the cap prevents a flaky network from stalling a job indefinitely.
4. **Attempt-scoped updates** — every job update may carry `expectedAttempt`; a callback belonging to an older attempt is discarded, so a late retry callback cannot resurrect a superseded attempt. Queue retries also increment a persisted `attempt` counter surfaced in the job detail line.
5. **Terminal-state guard** — `JobStateGuard` rejects state changes on terminal jobs (except idempotent repeats) and rejects progress/metadata updates on terminal jobs, so late callbacks cannot mutate finished or failed jobs.
6. **Cancellation checkpoints** — cancellation is checked before retries, before fallback, and around the transfer, and is propagated as `CancellationException` rather than being classified as a download failure.
7. **Browser fallback preserved** — when retries are exhausted, the existing browser-fallback path still runs; the retry loop does not bypass or replace it.

### Retry decision rules

| Failure category | Retry? | Conditions |
|---|---|---|
| `NETWORK_ERROR`, `TIMEOUT` | Yes | unless the host could not be resolved (permanent DNS markers) |
| `HTTP` | Yes | transient markers, or status 408 / 425 / 429 / 5xx |
| `HTTP` | No | 401 / 403 / 404 / 410 and other non-transient rejections |
| `CLOUDFLARE` | Yes | bot challenges are treated as potentially transient |
| Anything else | No | reported to the user immediately |
| Any category | No | if the transfer already started or a media URL was resolved |

A locally calculated checksum or the retry budget never converts a failure into a success claim; the UI reports the final outcome and the browser-fallback state machine remains authoritative.

## 4. Work Package 2 — Custom yt-dlp Runtimes (`487dde3`)

### 4.1 Source validation (`runtime/CustomRuntimeSource.kt`)

- Input is normalized to `owner/repo`; full `github.com/...` URLs are accepted, other schemes, SSH forms, and path traversal are rejected.
- Repositories managed as the stock runtime (`SecureComponentUpdater.REPO_STABLE`, `REPO_NIGHTLY`) cannot be installed as custom runtimes.
- Only releases whose asset is named **exactly `yt-dlp`** (the Python zipapp) and served from `https://github.com/` are considered. Platform-specific binaries (`yt-dlp_linux`, `.exe`, …) are never selected because they cannot run inside the bundled Python environment.
- Asset size must be positive and at most 64 MiB. The newest stable release is preferred; a prerelease is used only if no stable release publishes a usable asset.

### 4.2 Storage layout (`runtime/YtDlpRuntimeStore.kt`, `YtDlpRuntimeManager`)

- Custom binaries: `filesDir/yt-dlp-runtimes/<uuid>/yt-dlp`
- Metadata: `filesDir/ytdlp_runtimes.json` (repo, tag, asset name, SHA-256, probed version, timestamps, active selection)
- Stock binary: `noBackupFilesDir/youtubedl-android/yt-dlp/yt-dlp` — custom activation never modifies it.

### 4.3 Installation gates

A candidate is recorded as installed only after every gate passes:

1. Download to a temporary file; reject empty files and files above 64 MiB.
2. Reject a size mismatch against the published asset size.
3. Compute SHA-256 while streaming. The hash is **integrity metadata only**, never proof of publisher authenticity.
4. If the same tag is reinstalled and the hash changed, refuse to replace the binary.
5. Mark executable, then **execute the candidate** through the bundled `libpython.so` with the same environment contract the library uses, requiring exit code 0 and a reported version within 30 s. A binary that does not run is never installed.
6. Atomically move the verified file into place, then save metadata.

### 4.4 Activation and fail-closed behaviour

- Activation sets the library's private static `ytdlpPath` field to the verified binary path. This is reflection against a library internal and is safe only because the dependency is pinned (`io.github.junkfood02.youtubedl-android:library:0.18.1`); a library upgrade requires re-validation.
- If the active binary is missing or activation fails after an install, the selection is rolled back to stock and the failure is reported. Startup re-application (`applyActiveRuntime`) also fails closed to stock.
- Switching runtimes, installing, updating, and removing are refused while downloads are active (`busyPredicate`), and a single operation mutex prevents concurrent runtime operations. The active custom runtime cannot be removed until stock is selected.
- Update checks query the GitHub releases API per installed runtime; failures are reported per runtime and do not silently claim the runtime is current.
- There is no automatic download or execution of arbitrary repository content: only the single `yt-dlp` asset of an explicitly entered repository is downloaded, and it is executed only for the version probe and by normal download jobs.

## 5. Work Package 3 — Pre-Download Size Estimation (`aebe890`)

- **Preflight** (`SizeEstimator`): runs the active runtime with `--simulate --dump-single-json`, the same format selector the transfer will use, the same JS-runtime and session/header context, and a 12 s timeout. The process is reaped by unique ID on completion, timeout, or cancellation. A failed preflight yields `UNAVAILABLE` and never blocks or alters the download.
- **Calculation** (`SizeEstimateCalculator`): uses `filesize` when present (exact), `filesize_approx` otherwise (approximate); sums merged video+audio `requested_formats`; sums playlist entries honouring the selected start/end; scales trimmed ranges; derives audio re-encodes from the target MP3 bitrate or PCM geometry with documented defaults (48 kHz, 2 channels).
- **UI** (`HomeScreen`): the confirmation dialog shows checking, exact, approximate, or unavailable states, the media title, and the formatted size. Estimates are requested when the dialog opens; `SizeEstimateGate` generation tokens discard results belonging to a dismissed or superseded confirmation. A “skip future confirmations” action persists the existing `showDownloadSizeConfirmation` setting (default: enabled).
- **Honest labelling**: the UI distinguishes exact from approximate estimates. An estimate is not a guarantee that the final file has exactly that size.

## 6. Work Package 4 — Shared-Link Download Sheet (`fe7d40e`)

- `MainActivity` extracts the first HTTP(S) URL from shared text or a view intent, validates it, and suppresses duplicate deliveries of the same intent within 1.5 s (cold start, activity recreation, duplicate `onNewIntent`). Pending shares and the suppression fingerprint survive configuration changes via saved instance state.
- `ShareConfigSheet` presents Video / Audio / Commands tabs (Commands only when custom-command mode is enabled) and exposes the relevant quality, format, bitrate, subtitle, thumbnail, and template choices. `ShareRequestBuilder` maps the choices onto a `DownloadRequest`; command mode runs the selected template with subtitles and thumbnail embedding disabled.
- **Remember choices** persists only the sheet's options (`SharePreferencesCodec`) — no URL, headers, or tokens — and is independent of the global size-confirmation preference, so enabling it does not change the normal download dialog.
- Invalid or absent links do not open the sheet. The normal path (confirmation/location/estimate) still applies after the sheet is confirmed when those settings require it.

## 7. Work Package 5 — Exact URL in Browser-Fallback Diagnostics (`aee386e`)

- When a job reaches the browser fallback (a fallback attempt fails, or a resolved media URL exists), the diagnostic entry's acquisition method is recorded as `Browser Fallback`, and the **original request URL is preserved verbatim**, including its query string, so the page that failed can actually be reproduced.
- Every other diagnostic URL remains sanitized (sensitive path segments and query values redacted). Headers, cookies, and log tails remain redacted in all entries. Diagnostics are stored locally and are exported only by an explicit user action; nothing is uploaded automatically.

### 8.3 Fallbacks and accessibility

- **No backdrop / no RenderEffect (API < 31)**: the bar renders a static translucent surface (70% light / 68% dark); no lens is drawn. The nav remains fully usable.
- **API < 33 (no runtime shaders)**: blur and tint remain; the bar and held lens skip `lens()` and fall back to a plain translucent rim.
- **High contrast**: read from `Settings.Secure.high_text_contrast_enabled`; the held lens is disabled (resting capsule only), matching Mornye's contrast-block policy.
- **Reduced motion** (`ValueAnimator.areAnimatorsEnabled() == false`): the held lens is disabled and the pill jumps between slots; the active-item lift is disabled. Touch targets and selection semantics are unchanged.
- **RTL**: slot positions come from measured physical bounds, so the indicator and held lens stay on the pressed destination; the row itself mirrors automatically.
- **Touch targets**: 54dp-tall pill/slots inside the 64dp bar, unchanged per-item click semantics, haptics preserved.
- **Icons never resize**: the glass scales on press; icons and labels do not.

### 8.4 Mapping limitations (honest differences)

- `liquid_glass_easy` models a refraction index and fixed 70px edge bend; the vendored Kyant0 lens models a refraction band with a magnification factor. The documented mapping is `refractionWidth → refractionHeight`, `refractionWidth × refractionDepth → refractionAmount`, derived index → `magnification` (1.171 bar / 1.018 held lens), and dispersion → the shader's chromatic-aberration flag. Kyant's magnification affects the whole sampled area, so the optical result is an approximation, not an arithmetic identity.
- Mornye's multi-layer specular/glow is approximated with `Highlight` plus the existing rim; exact light falloff is not part of the vendored library.
- The bar's refraction depth stays at its resting 0.45; Mornye animates it to 0.60 while pressed. VRKA's press refraction is carried by the held lens so the bar's full-width capture does not re-run every press frame.
- Mornye's `mornye_selection_mask.frag` icon/label recolor is not ported (VRKA identity: purple selected icon, grey labels). Foreground text/icons are not recoloured by the moving pill.
- No Mornye appearance setting, global theme change, or other-screen restyle was added.

### 8.5 Device verification status

Manual verification on a OnePlus 11 was **not performed** in this environment. Consequently:

- The verified claim is limited to: geometry/policy helpers are unit-tested, the code compiles, the full suite and lint pass, and the debug APK builds.
- Visual parity, animation feel, GPU shader output, and the nested bar-capture/held-lens path remain **unverified on hardware** and must be checked on-device before any release note claims parity.
- No screenshot/render golden tests were added: the project has no Robolectric or Compose UI-test harness, and instrumented tests require a connected device.

### 8.6 Rendering-cost corrections

Rapid tab switches and horizontal swipes were re-investigated against the vendored backdrop implementation (`DrawBackdropElement.update`, `LayerBackdropNode.draw`). The appearance was not the problem; work was being repeated every frame for state that had not changed. Four mechanisms were corrected:

| # | Root cause | Correction |
|---|---|---|
| 1 | `VrkaRoot` read `pagerState.currentPage + currentPageOffsetFraction` as a parameter value, so every swipe frame recomposed the whole bar | A remembered `pagerPositionProvider: (() -> Float)` lets the bar pull the position inside a `snapshotFlow` coroutine; pager motion invalidates draw/layout, never composition |
| 2 | The press state was snapshot state read in composition (`isPressing` + `LaunchedEffect`), recomposing the bar twice per touch | The 240ms press animation starts and releases directly from the pointer gesture on `Animatable`; the press flag is gone. Recomposition now happens only when the lens enters/leaves composition (0 → >0 → 0) |
| 3 | `NavPressLens` read `pressProgress.value` in composition, rebuilding its size, effects, highlight and surface lambdas on all ~15 press frames | Bounds are resolved in `Modifier.layout`; effects, highlight, surface wash and outline read `pressProgress.value` at draw time from lambdas created once |
| 4 | `ShapeProvider` has no `equals`, so `DrawBackdropElement.update` treated freshly allocated lambdas as a changed capture and re-recorded the backdrop + re-ran blur/lens on every recomposition | The bar's whole `drawBackdrop` modifier, its ambient-shadow draw block and its glass scale layer are `remember`ed for the lifetime of the bar |

Geometry and appearance are unchanged: 64dp bar, 54dp resting pill, 32dp radii, 20dp margin, 6dp inset, VRKA purple, existing icons, English labels, four destinations, swipe and drag behaviour, glass, refraction, lens and press effects. No safety mechanism, fallback, accessibility path or reduced-motion path was removed.

## 9. Work Package 7 — Per-Job Runtime Recording (`29916ae`)

- When a direct transfer starts, the job snapshot records the active runtime description and normalized version (`DownloadJob.runtimeName`, `runtimeVersion`). This snapshot is accurate for the job's whole lifetime because runtime switching is refused while jobs are active.
- `JobStore` persists both fields, so they survive history reloads and later runtime switches.
- The user-copied diagnostic report gains a `Runtime:` line (e.g. `Custom owner/repo nightly • yt-dlp 2026.10.01`), sanitized and capped at 160 characters. It contains no headers, cookies, or secrets, and is never uploaded automatically.

## 11. Known Limitations

1. **OnePlus 11 manual verification was not performed.** No navigation-parity claim is made, and no download-can-never-fail claim is made.
2. **Navigation shader output is hardware-dependent and unverified**; the non-shader fallback is the implementation used when RenderEffect/runtime shaders are unavailable. The Flutter→Compose optical parameter mapping is an approximation (§8.4).
3. **Custom runtime activation uses reflection** into `ytdl-android` 0.18.1 internals (`ytdlpPath`). Upgrading the dependency requires re-validating §4.4.
4. **Custom runtime authenticity is not established.** SHA-256 is computed locally for integrity and tamper detection; it is not a publisher signature. Users are warned that custom forks are unverified third-party code.
5. **GitHub API rate limits** can make install/update checks fail; failures are surfaced as errors, not as “up to date”.
6. **Size estimates are approximations** for transcodes, trims, and variable-bitrate sources; they never block downloads and can differ from the final file size.
7. **Browser fallback availability depends on the device browser** and the page; it is a recovery path, not a guarantee.
8. **Translations were authored in this work without native-speaker review.** Key parity and placeholder/XML validity are verified; linguistic quality should be reviewed before publishing.
9. **Only a debug APK was built.** Production signing, tags, releases, and pushing were intentionally not touched.
10. No F-Droid-related commits, branches, patches, metadata, or implementation changes were used.

## 12. Security Invariants Preserved

- No new runtime permissions and no `SYSTEM_ALERT_WINDOW`; no system-wide overlay.
- No DRM, authentication, CAPTCHA, or access-control bypass.
- No arbitrary execution of GitHub repository contents (only the exact `yt-dlp` asset, only after size/integrity/execution gates).
- Existing security checks (header validation, URL validation, component update verification) remain in place.
- Authentication headers, cookies, and unrelated secrets are not logged; diagnostics are local and user-exported only.
- A locally calculated checksum is never presented as publisher authenticity.
- A custom fork is never marked valid unless its execution was actually verified.
