## 4. Work Package 3 — Size Estimation Repair (`0d6405e`)

Real yt-dlp `--dump-single-json` output stores merged-stream sizes under `requested_downloads[0].requested_formats`, with a null top-level `filesize`. The previous calculator only read top-level `requested_formats`, so merged downloads often appeared unavailable or were understated.

The repaired pipeline:

1. Reads both metadata shapes: top-level `requested_formats` and nested `requested_downloads[0].requested_formats`.
2. Uses `filesize` only when it is genuinely exact; otherwise uses `filesize_approx`, bitrate-derived sizes, or sums of merged components.
3. Labels merged sums, approximate sizes, trims, and audio re-encodes as **APPROXIMATE**; only a single exact stream is **EXACT**; missing data is **UNAVAILABLE**.
4. Never blocks a download when estimation fails; the confirmation dialog offers retry and skip paths.
5. `MetadataEstimateCache` bounds metadata reuse with a TTL/LRU policy keyed by URL, format selection, runtime, and request context. It does not store cookies; in-flight requests for the same key are de-duplicated.
6. A realistic trimmed "Me at the zoo" fixture (`ytdlp/youtube-merged.json`) exercises the actual merged shape.

Verification: `SizeEstimateTest` (23 tests) and `MetadataEstimateCacheTest` (7 tests) run offline against fixtures, not live sites.

## 5. Work Package 4 — Download Pipeline Optimization (`d6eabec`)

Structural changes, each with a test:

1. **One extraction per job instead of two** — the transfer already prints the resolved title (`__VRKA_TITLE__`), so the separate `getInfo()` probe before each direct transfer was removed. Jobs receive their title as soon as extraction starts.
2. **Reusable yt-dlp cache** — `DownloadRequestFactory` restores an app-private `--cache-dir` (`cacheDir/yt-dlp`) for info, size estimation, downloads, subtitle extraction, and fallback probes. This lets player/signature data be reused within a job and across retries. ytdl-android's forced `--no-cache-dir` is only injected when no cache directory is supplied; custom command templates keep their own cache policy, and an explicit `--no-cache-dir` is respected.
3. **No redundant `ejs:github` component request** — the bundled `yt_dlp_ejs` runtime already provides the JS challenge solver; the remote component request was dropped.
4. **Bounded fragment concurrency retained** at 4 concurrent fragments; no unbounded parallelism was introduced.

Verification: `DownloadRequestFactoryTest` (21 tests) asserts cache-directory presence/absence, absence of `--remote-components`, and fragment concurrency. Tests do not call the network.

**Performance claim limitation**: no on-device A/B timing against Seal was possible here. The verified improvement is structural: one fewer full yt-dlp metadata invocation per direct job, plus cache reuse. No "faster than Seal" claim is made.

## 6. Work Package 5 — Navbar Performance and Geometry (`d12dec1`)

- Selection state is derived (`derivedStateOf`) and the moving pill is painted in `drawBehind`; continuous pager/drag position is read only in draw and `graphicsLayer` phases. This avoids per-frame recomposition of the bar and its items.

- The held press lens was extracted into `NavPressLens`, gated by reduced motion and high contrast.

- `NavIndicatorGeometryTest` (18 tests) covers slot geometry, pill bounds, RTL, pager synchronization, press-lens growth/clamping, reduced-motion/high-contrast gating, bar/pill dimension ranges, selected-index rounding, and item-focus falloff.

## 8. Work Package 7 — Download Notification Progress (final state)

### 8.1 What the app posts

- Every active download posts an ordinary progress notification built with `NotificationCompat`:
  determinate `setProgress(100, percent, false)` while transferring, indeterminate while
  preparing/queued/postprocessing, `setOngoing(true)`, category `PROGRESS`, a localized state
  subtext, and a Cancel action.
- `setForegroundServiceBehavior(IMMEDIATE)` keeps the first foreground notification from being
  deferred on Android 12+.
- No custom RemoteViews, no progress tracker glyph, no promotion request and no colorized flag are
  attached. The platform draws the notification entirely.

### 8.2 Stable per-job identifiers and lifecycle

- Each job's notification id is `4200 + (jobId.hashCode() and 0xFFFF)`, so updates replace the same notification instead of stacking duplicates, and ids are stable across preparing → downloading → postprocessing.
- The first active job owns the foreground notification; additional active jobs are posted individually with their own ids.
- Notifications for jobs that leave the active set are cancelled. When the service becomes idle or is destroyed, the foreground notification and all per-job notifications are removed.
- `onStartCommand` remains `START_NOT_STICKY`; cancellation and stop-if-idle paths resynchronise the notification set immediately.
- **Timeout fallback (API 35+ `onTimeout`)**: when Android ends the data-sync foreground window, the service stops foreground mode, clears per-job notifications, and posts an auto-cancel "Downloads paused" notification with an **Open queue** action. The service then stops; downloads are not silently presented as complete.

### 8.3 User-facing strings

Three strings were added in all 14 locale sets:

- `notification_downloads_interrupted_title`
- `notification_downloads_interrupted_text`
- `btn_open_queue`

`DownloadNotificationTest` covers stable/distinct notification ids, determinate/indeterminate
progress selection (including NaN and infinity), the absence of any promotion request, and the
absence of a progress tracker extra.

### 8.4 Removed: Live Update promotion

Earlier revisions of this branch implemented the Android 16 promoted Live Update path
(`Notification.ProgressStyle`, the `android.requestPromotedOngoing` extra, the manifest-only
`POST_PROMOTED_NOTIFICATIONS` permission, a progress-tracker icon, a Settings row and five strings
per locale). Promotion acceptance could never be observed: the available API 36.0 emulator image
cannot grant promotion to any third-party app, and no physical Android device could be attached for
testing. The v5.1.0 stabilization package therefore required the unverified feature to be removed
rather than kept behind a gate. `DownloadNotifications` no longer contains any promotion code, the
manifest no longer declares the permission or the promotion settings `<queries>`, and the Settings
screen no longer offers a Live Updates row.

## 11. Known Limitations

1. **No device verification.** No Android device was attached; all UI, notification, animation, and timing claims are limited to compilation, unit tests, lint, and APK assembly.
2. **No benchmark against Seal.** Pipeline changes are structural; no on-device speed comparison was run and no superiority claim is made.
3. **No Live Alerts.** Promotion could not be verified on any attachable device, so the Live Update
   path was removed for v5.1.0 (see §8.4 and §14.11). Downloads use the ordinary platform progress
   notification on every API level.
4. **Data-sync foreground timeout** is handled with a fallback notification and service stop; interrupted downloads are not automatically resumed. This path is unverified on hardware.
5. **Secondary job notifications** require notification permission on Android 13+; without it, only the foreground-service notice remains visible to the system.
6. **Size estimates remain estimates** for merged, variable-bitrate, trimmed, and re-encoded media.
7. **Glow and glass rendering are GPU/device dependent**; fallbacks exist but were not visually verified.
8. **Debug APK only.** Production signing, tags, releases, and pushes were intentionally left untouched.
9. No F-Droid-related changes were used at any point.

## 14. Phase 2 — Regression Correction, UI Restoration, Download Reliability and Emulator QA

This section records the follow-up pass requested after v5.1.0 regression reports. All work stays on `feature/v5.1.0-localization-release-base`, keeps `versionCode 50100` / `versionName "5.1.0"`, and does not amend, push, tag, or sign anything.

### 14.1 Navbar geometry and label fit (WP1)

- Restored the fd12ad5 reference geometry: 64dp bar, 54dp resting pill (64dp − 2×5dp vertical inset), 32dp bar and pill radii, 6dp horizontal tab inset.
- Nav item content receives 8dp horizontal padding inside the slot, so the label glyph box sits 2dp inside the pill edge; label type is 10sp/12sp line height (down from 11sp), one line, ellipsized, mono.
- Press lens, blur/refraction/glass layers and the 28%/24% held expansion are preserved; the lens is only recorded while visible.
- Continuous selection position is read only in draw and `graphicsLayer` phases; only the boolean selected/unselected flip recomposes.
- `NavIndicatorGeometryTest` covers the restored dimensions and bounds.
- **Not claimed:** 120Hz frame-timing measurements. The only available emulator uses software GPU and ARM translation, so frame data from it would not represent a device.

### 14.2 Progress bar restoration (WP2)

- `VrkaGlowProgressBar` now draws a continuous track, solid purple gradient fill, near-white leading head and a restrained radial head glow plus a short trailing gradient. The head is clamped to the fill, and nothing animates on its own: no pulse, no travelling sheen, no particles.
- Paints are allocated once per size and re-shaded only on canvas-size change; progress reads happen only in the draw phase.
- Notification progress no longer adds a custom tracker icon; the system-drawn determinate `ProgressStyle` bar is used instead (see §14.6).

### 14.3 Queue size restoration (WP3)

- `DownloadJob` persists `downloadedBytes`, `totalBytes`, and `totalIsExact` through `JobStore`, so sizes survive relaunch, service recreation and history reload.
- Native path: throttled yt-dlp progress lines are parsed (`12.4% of 48.20MiB` and `of ~ 48.20MiB`) into byte counts; the final published file size is used on completion.
- Media-engine/fallback path: `EngineDownloadProgress.bytesRead/totalBytes` and `EngineExecutionResult.totalBytes` are recorded; fallback completion derives the total from the published file.
- Queue and strip cards render `Downloaded 12.4 MiB / 48.2 MiB`, `Downloaded 12.4 MiB / ~48.2 MiB`, `Downloaded 12.4 MiB / calculating size`, and `Completed · 48.2 MiB` from 6 new localized strings. Rows are never hidden while a transfer is active; unknown sizes show `Calculating size`.
- No extra metadata request is issued per card.

### 14.4 Single-attempt downloads (WP4)

- `RetryPolicy` and its automatic-retry countdown were removed; `MAX_NATIVE_TRANSFER_ATTEMPTS = 1` documents the contract.
- A classified native failure falls through to browser fallback immediately; an unclassified failure becomes a permanent job failure with a manual Retry action. No `Retrying in 2s (attempt 2 of 3)` state can be produced.
- The recovery-attempt branch (impersonation flag, forced UA/referer) was removed from `DownloadRequestFactory`.
- `SingleAttemptPolicyTest`, `JobStateGuardTest`, and updated `DownloadRequestFactoryTest` pin the behaviour.

### 14.5 Estimation latency (WP5)

- The share sheet's first preflight runs immediately (no debounce); only later selection changes are debounced, and size metadata no longer blocks `Add to Queue`.
- The metadata document from one yt-dlp probe is cached and reused; quality changes recalculate locally via `SizeEstimateCalculator.fromMetadataJson`.
- `MetadataEstimateCache` deduplicates in-flight probes and bounds entries by TTL/LRU.
- **Not claimed:** measured seconds-to-first-card. No physical device was attached, and the x86_64 emulator cannot execute the ARM64 yt-dlp/ffmpeg binaries, so no latency numbers are reported.

### 14.11 Live Alerts: Outcome B — the feature was removed

Reported symptom: the download notification showed a moving glyph under the progress bar and the
system never displayed a promoted Live Alert, while Settings offered a Live Updates entry.

The earlier correction attempted to satisfy the platform contract on both Android 16.0 and 16 QPR1
semantics (runtime probe of `hasPromotableCharacteristics()`, request extra, conditional colorizing,
a transparent tracker icon, and a gated Settings row). The structural contract was satisfied on the
API 36.0 emulator and the tracker glyph disappeared, but the promoted state itself was never
observed: that image cannot grant promotion to any third-party app
(`canPostPromotedNotifications() == false`, no `POST_PROMOTED_NOTIFICATIONS` in `framework-res`),
and no physical Android device was ever attached. `adb devices -l` listed only `emulator-5554`
during the final package.

The v5.1.0 stabilization package is explicit about this case: if the physical device cannot be
tested through ADB, do not claim successful promotion and implement Outcome B instead of keeping an
unverified feature. Outcome B was therefore applied:

- Removed the `Notification.ProgressStyle` construction, the promotion probe, the
  `android.requestPromotedOngoing` extra, and all colorized handling from `DownloadNotifications`.
- Removed `POST_PROMOTED_NOTIFICATIONS` and the promotion settings `<queries>` block from the
  manifest.
- Removed the Settings "Live Updates" row, the promotion helpers, and the About-section entry.
- Removed the five Live Update strings from all 14 locale sets.
- Deleted the transparent tracker drawable; standard progress notifications set no tracker at all.
- Removed the obsolete promotion unit/instrumentation tests and replaced them with tests that assert
  the absence of promotion: no request extra, no colorized flag, no tracker extra,
  `hasPromotableCharacteristics() == false` on Android 16, and no manifest permission.

The standard download notification is unchanged in what the user sees: title, localized state,
progress bar, ongoing while transferring, Cancel action, and the standalone post-completion record
documented in §14.13.

### 14.13 Post-completion notification

A finished download now posts its own record instead of silently disappearing from the shade:

- A dedicated channel (`vrka_downloads_complete`, `IMPORTANCE_DEFAULT`, badges on) and a
  tag-derived identity (`completed:<jobId>`, id `100100`) place the record outside the active
  transfer id range, so the foreground service's and the transfer job's idle cleanup cannot cancel
  it. It also survives the service stop and the user-initiated transfer handoff.
- The record shows the job title, the localized completed state, the actual published file size
  (read back from the content provider, never the pre-merge estimate) and the posting time. It is
  dismissible, auto-cancel, non-ongoing, and independent per job.
- Tapping it opens the published content URI with the provider's MIME type and a read grant; a
  visible **Open** action does the same. When no viewer resolves, both fall back to the queue.
- Posting is guarded by `state == DONE`, a non-empty output list and the notification permission, so
  failures, cancellations and retries can never post a completion.
- `CompletionNotificationTest` (7 instrumentation tests) verifies one dismissible record per job,
  the published-size text, no completion for failed/cancelled jobs, survival of notification
  cleanup, distinct records for concurrent completions, the content-URI/MIME open action, and the
  announcing/badged channel.
