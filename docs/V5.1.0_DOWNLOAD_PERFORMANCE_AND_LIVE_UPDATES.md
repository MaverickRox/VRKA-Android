## 4. Work Package 3 — Size Estimation Repair (`0d6405e`)

Real yt-dlp `--dump-single-json` output stores merged-stream sizes under `requested_downloads[0].requested_formats`, with a null top-level `filesize`. The previous calculator only read top-level `requested_formats`, so merged downloads often appeared unavailable or were understated.

The repaired pipeline:

1. Reads both metadata shapes: top-level `requested_formats` and nested `requested_downloads[0].requested_formats`.
2. Uses `filesize` only when it is genuinely exact; otherwise uses `filesize_approx`, bitrate-derived sizes, or sums of merged components.
3. Labels merged sums, approximate sizes, trims, and audio re-encodes as **APPROXIMATE**; only a single exact stream is **EXACT**; missing data is **UNAVAILABLE**.
4. Never blocks a download when estimation fails; the confirmation dialog offers retry and skip paths.
5. `MetadataEstimateCache` bounds metadata reuse with a TTL/LRU policy keyed by URL, format selection, runtime, and request context. It does not store cookies; in-flight requests for the same key are de-duplicated.
6. A realistic trimmed "Me at the zoo" fixture (`ytdlp/youtube-merged.json`) exercises the actual merged shape.

Verification: `SizeEstimateTest` (23 tests) and `MetadataEstimateCacheTest` (7 tests) run offline against fixtures, not live sites.

## 5. Work Package 4 — Download Pipeline Optimization (`d6eabec`)

Structural changes, each with a test:

1. **One extraction per job instead of two** — the transfer already prints the resolved title (`__VRKA_TITLE__`), so the separate `getInfo()` probe before each direct transfer was removed. Jobs receive their title as soon as extraction starts.
2. **Reusable yt-dlp cache** — `DownloadRequestFactory` restores an app-private `--cache-dir` (`cacheDir/yt-dlp`) for info, size estimation, downloads, subtitle extraction, and fallback probes. This lets player/signature data be reused within a job and across retries. ytdl-android's forced `--no-cache-dir` is only injected when no cache directory is supplied; custom command templates keep their own cache policy, and an explicit `--no-cache-dir` is respected.
3. **No redundant `ejs:github` component request** — the bundled `yt_dlp_ejs` runtime already provides the JS challenge solver; the remote component request was dropped.
4. **Bounded fragment concurrency retained** at 4 concurrent fragments; no unbounded parallelism was introduced.

Verification: `DownloadRequestFactoryTest` (21 tests) asserts cache-directory presence/absence, absence of `--remote-components`, and fragment concurrency. Tests do not call the network.

**Performance claim limitation**: no on-device A/B timing against Seal was possible here. The verified improvement is structural: one fewer full yt-dlp metadata invocation per direct job, plus cache reuse. No "faster than Seal" claim is made.

## 8. Work Package 7 — Android Live Update Notifications (`9ab9129`, `c47e75c`)

### 9.1 API usage

- **Android 16+ (`SDK_INT >= 36`)**: notifications are built with `Notification.Builder` and `Notification.ProgressStyle`:
  - determinate `setProgress(0..100)` while transferring;
  - indeterminate progress while preparing/postprocessing/queued;
  - a fully transparent progress tracker icon, so no moving marker is drawn;
  - ongoing, low-importance channel, category `PROGRESS`.
- **Promotion request**: the documented `android.requestPromotedOngoing` extra is always set on job
  notifications. The visual contract is chosen at runtime by asking the platform, not by a version
  number: a probe notification carrying the request and no colorized flag is checked with
  `Notification.hasPromotableCharacteristics()`. If the platform accepts it, Android 16 QPR1
  semantics are live and the real notification is left uncolorized; otherwise Android 16.0
  semantics apply and the notification requests colorizing. The result is cached per process.
- `POST_PROMOTED_NOTIFICATIONS` is declared in the manifest (non-runtime; no prompt). The actual
  user permission is read with `NotificationManager.canPostPromotedNotifications()`.
- **Below API 36**: the existing `NotificationCompat` path is used unchanged, with progress and cancel action preserved.

Why a probe instead of `SDK_INT_FULL`: the QPR1 contract is behind the `uiRichOngoing` flag
(`Notification.hasPromotableCharacteristics()` falls back to the 36.0 rule when it is off), and
OEM builds can backport either behaviour. The probe tests the behaviour that is actually active.

### 9.2 Stable per-job identifiers and lifecycle

- Each job's notification id is `4200 + (jobId.hashCode() and 0xFFFF)`, so updates replace the same notification instead of stacking duplicates, and ids are stable across preparing → downloading → postprocessing.
- The first active job owns the foreground notification; additional active jobs are posted individually with their own ids.
- Notifications for jobs that leave the active set are cancelled. When the service becomes idle or is destroyed, the foreground notification and all per-job notifications are removed.
- `onStartCommand` remains `START_NOT_STICKY`; cancellation and stop-if-idle paths resynchronise the notification set immediately.
- **Timeout fallback (API 35+ `onTimeout`)**: when Android ends the data-sync foreground window, the service stops foreground mode, clears per-job notifications, and posts an auto-cancel "Downloads paused" notification with an **Open queue** action. The service then stops; downloads are not silently presented as complete.

### 9.3 New user-facing strings

Three strings were added in all 14 locale sets:

- `notification_downloads_interrupted_title`
- `notification_downloads_interrupted_text`
- `btn_open_queue`

`DownloadNotificationTest` (3 tests) covers stable/distinct notification ids and determinate/indeterminate progress selection, including NaN and infinity.

### 9.4 Honest limitation

The promotion request can be constructed and verified structurally, but whether the system actually
promotes a notification depends on the OS build and the per-app user permission. The API 36.0
emulator image used for this work does not define `POST_PROMOTED_NOTIFICATIONS` at all, so
`canPostPromotedNotifications()` is permanently false there and the Live Updates row is hidden.
The promotion flag itself was therefore not observed on this image; see §14.11 for the evidence
that was collected and the remaining device gap.

## 11. Known Limitations

1. **No device verification.** No Android device was attached; all UI, notification, animation, and timing claims are limited to compilation, unit tests, lint, and APK assembly.
2. **No benchmark against Seal.** Pipeline changes are structural; no on-device speed comparison was run and no superiority claim is made.
3. **Live Alerts promotion is OS- and user-gated.** The app always requests promotion on Android 16+,
   but the system only promotes when the build defines the promotion permission, the user allows it,
   and the notification is structurally eligible. On builds without that support the Settings row is
   hidden and the ordinary progress notification is used. Actual promotion was not observed on an
   Android 16.1+ build or on the target OnePlus device (not attached).
4. **Data-sync foreground timeout** is handled with a fallback notification and service stop; interrupted downloads are not automatically resumed. This path is unverified on hardware.
5. **Secondary job notifications** require notification permission on Android 13+; without it, only the foreground-service notice remains visible to the system.
6. **Size estimates remain estimates** for merged, variable-bitrate, trimmed, and re-encoded media.
7. **Glow and glass rendering are GPU/device dependent**; fallbacks exist but were not visually verified.
8. **Debug APK only.** Production signing, tags, releases, and pushes were intentionally left untouched.
9. No F-Droid-related changes were used at any point.

- `DownloadJob` persists `downloadedBytes`, `totalBytes`, and `totalIsExact` through `JobStore`, so sizes survive relaunch, service recreation and history reload.

- `RetryPolicy` and its automatic-retry countdown were removed; `MAX_NATIVE_TRANSFER_ATTEMPTS = 1` documents the contract.

- The recovery-attempt branch (impersonation flag, forced UA/referer) was removed from `DownloadRequestFactory`.
- `SingleAttemptPolicyTest`, `JobStateGuardTest`, and updated `DownloadRequestFactoryTest` pin the behaviour.

### 14.11 Live Alerts correction (v5.1.0 review)

Reported symptom: the download notification showed a moving glyph under the progress bar and the
system never displayed a promoted Live Alert, while Settings offered a Live Updates entry.

**Evidence correction.** The "Sports from Google" notification-settings screenshot is Google's page,
not VRKA's, and is not evidence about VRKA. The VRKA page (title `VRKA`, switch "Show Live Updates on
Live Alerts") is the relevant one. The About row must therefore open VRKA's own package page, never
another app's page.

**Root causes found**

1. Promotion was gated on `SDK_INT_FULL >= 36.1`, and `hasPromotableCharacteristics()` was consulted
   *before* the request extra was attached, so on 36.1-capable builds the request was never emitted.
2. On Android 16.0, `hasPromotableCharacteristics()` returns false unless the notification is
   colorized (AOSP `android16-release`, `Notification.java:3297-3306`). The notification never
   requested colorizing, so it was structurally ineligible.
3. Android 16 QPR1 inverts the rule: the request extra is required and colorized is disqualifying
   (AOSP `android16-qpr1-release`, `Notification.java:3388-3407`). QPR1 gates this behind the
   `uiRichOngoing` flag and otherwise falls back to the 36.0 rule, so a version number alone cannot
   select the contract.
4. The Settings entry was shown on any Android 16 build and used no package-scoped intent validation,

5. The moving marker was a SystemUI fallback for an unset tracker icon; our code had never set one.

**Corrections**

- The contract is now selected by a cached runtime probe (`hasPromotableCharacteristics()` on a
  request-carrying, non-colorized probe notification), not by `SDK_INT_FULL`. The documented request
  extra is always present; colorizing is requested only when the platform still uses the 16.0 rule.
- The tracker icon is an explicit fully transparent drawable; the instrumentation test renders it and
  asserts every pixel has alpha 0.
- The Settings row is shown only when the OS defines `POST_PROMOTED_NOTIFICATIONS` or resolves the
  promotion settings action. The intent carries `EXTRA_APP_PACKAGE = context.packageName`, resolves
  before launch, falls back to the app notification page, and the enabled state is re-read on resume.
- `POST_PROMOTED_NOTIFICATIONS` remains the only promotion-related permission; the request extra is
  never turned into a locally-set flag.
