## 4. Work Package 3 — Size Estimation Repair (`0d6405e`)

Real yt-dlp `--dump-single-json` output stores merged-stream sizes under `requested_downloads[0].requested_formats`, with a null top-level `filesize`. The previous calculator only read top-level `requested_formats`, so merged downloads often appeared unavailable or were understated.

The repaired pipeline:

1. Reads both metadata shapes: top-level `requested_formats` and nested `requested_downloads[0].requested_formats`.
2. Uses `filesize` only when it is genuinely exact; otherwise uses `filesize_approx`, bitrate-derived sizes, or sums of merged components.
3. Labels merged sums, approximate sizes, trims, and audio re-encodes as **APPROXIMATE**; only a single exact stream is **EXACT**; missing data is **UNAVAILABLE**.
4. Never blocks a download when estimation fails; the confirmation dialog offers retry and skip paths.
5. `MetadataEstimateCache` bounds metadata reuse with a TTL/LRU policy keyed by URL, format selection, runtime, and request context. It does not store cookies; in-flight requests for the same key are de-duplicated.
6. A realistic trimmed "Me at the zoo" fixture (`ytdlp/youtube-merged.json`) exercises the actual merged shape.

Verification: `SizeEstimateTest` (23 tests) and `MetadataEstimateCacheTest` (7 tests) run offline against fixtures, not live sites.

**Superseded by §16.2.** The cache described here still backed one metadata run per format selection. Phase 4 removes `-f` from the preflight, stores the complete document once per source and calculates every format locally.

## 5. Work Package 4 — Download Pipeline Optimization (`d6eabec`)

Structural changes, each with a test:

1. **One extraction per job instead of two** — the transfer already prints the resolved title (`__VRKA_TITLE__`), so the separate `getInfo()` probe before each direct transfer was removed. Jobs receive their title as soon as extraction starts.
2. **Reusable yt-dlp cache** — `DownloadRequestFactory` restores an app-private `--cache-dir` (`cacheDir/yt-dlp`) for info, size estimation, downloads, subtitle extraction, and fallback probes. This lets player/signature data be reused within a job and across retries. ytdl-android's forced `--no-cache-dir` is only injected when no cache directory is supplied; custom command templates keep their own cache policy, and an explicit `--no-cache-dir` is respected.
3. **No redundant `ejs:github` component request** — the bundled `yt_dlp_ejs` runtime already provides the JS challenge solver; the remote component request was dropped.
4. **Bounded fragment concurrency retained** at 4 concurrent fragments; no unbounded parallelism was introduced.

Verification: `DownloadRequestFactoryTest` (21 tests) asserts cache-directory presence/absence, absence of `--remote-components`, and fragment concurrency. Tests do not call the network.

**Performance claim limitation**: no on-device A/B timing against Seal was possible here. The verified improvement is structural: one fewer full yt-dlp metadata invocation per direct job, plus cache reuse. No "faster than Seal" claim is made.

## 8. Work Package 7 — Download Notification Progress (final state)

### 8.1 What the app posts

- Every active download posts an ordinary progress notification built with `NotificationCompat`:
  determinate `setProgress(100, percent, false)` while transferring, indeterminate while
  preparing/queued/postprocessing, `setOngoing(true)`, category `PROGRESS`, a localized state
  subtext, and a Cancel action.
- `setForegroundServiceBehavior(IMMEDIATE)` keeps the first foreground notification from being
  deferred on Android 12+.
- No custom RemoteViews, no progress tracker glyph, no promotion request and no colorized flag are
  attached. The platform draws the notification entirely.

### 8.2 Stable per-job identifiers and lifecycle

- Each job's notification id is `4200 + (jobId.hashCode() and 0xFFFF)`, so updates replace the same notification instead of stacking duplicates, and ids are stable across preparing → downloading → postprocessing.
- The first active job owns the foreground notification; additional active jobs are posted individually with their own ids.
- Notifications for jobs that leave the active set are cancelled. When the service becomes idle or is destroyed, the foreground notification and all per-job notifications are removed.
- `onStartCommand` remains `START_NOT_STICKY`; cancellation and stop-if-idle paths resynchronise the notification set immediately.
- **Timeout fallback (API 35+ `onTimeout`)**: when Android ends the data-sync foreground window, the service stops foreground mode, clears per-job notifications, and posts an auto-cancel "Downloads paused" notification with an **Open queue** action. The service then stops; downloads are not silently presented as complete.

### 8.3 User-facing strings

Three strings were added in all 14 locale sets:

- `notification_downloads_interrupted_title`
- `notification_downloads_interrupted_text`
- `btn_open_queue`

`DownloadNotificationTest` covers stable/distinct notification ids, determinate/indeterminate
progress selection (including NaN and infinity), the absence of any promotion request, and the
absence of a progress tracker extra.

### 8.4 Removed: Live Update promotion

Earlier revisions of this branch implemented the Android 16 promoted Live Update path
(`Notification.ProgressStyle`, the `android.requestPromotedOngoing` extra, the manifest-only
`POST_PROMOTED_NOTIFICATIONS` permission, a progress-tracker icon, a Settings row and five strings
per locale). Promotion acceptance could never be observed: the available API 36.0 emulator image
cannot grant promotion to any third-party app, and no physical Android device could be attached for
testing. The v5.1.0 stabilization package therefore required the unverified feature to be removed
rather than kept behind a gate. `DownloadNotifications` no longer contains any promotion code, the
manifest no longer declares the permission or the promotion settings `<queries>`, and the Settings
screen no longer offers a Live Updates row.

## 11. Known Limitations

1. **No physical-device verification.** An Android 16 (API 36) emulator was attached in Phases 2–3, so UI, notification and component-version claims now have emulator runtime evidence; no OnePlus 11 or other hardware was available, so GPU rendering, 120 Hz frame timing, real transfers and platform notification layout on a production phone remain unverified (§15.11, §15.14).
2. **No benchmark against Seal.** Pipeline changes are structural; the x86_64 emulator cannot execute the shipped ARM64 yt-dlp/ffmpeg binaries and no phone was attached, so no speed or metadata-latency measurement against Seal was run and no superiority claim is made (§15.9).
3. **No Live Alerts.** Promotion could not be verified on any attachable device, so the Live Update
   path was removed for v5.1.0 (see §8.4 and §14.11). Downloads use the ordinary platform progress
   notification on every API level.
4. **Data-sync foreground timeout** is handled with a fallback notification and service stop; interrupted downloads are not automatically resumed. This path is unverified on hardware.
5. **Secondary job notifications** require notification permission on Android 13+; without it, only the foreground-service notice remains visible to the system.
6. **Size estimates remain estimates** for merged, variable-bitrate, trimmed, and re-encoded media.
7. **Glow and glass rendering are GPU/device dependent**; the glow bar was visually verified on the software-rendered emulator (§8.7 of the hardening document) and the glass navbar was not measured on hardware.
8. **Debug APK only.** Production signing, tags, releases, and pushes were intentionally left untouched.
9. No F-Droid-related changes were used at any point.

- `VrkaGlowProgressBar` now draws a continuous track, solid purple gradient fill, near-white leading head and a restrained radial head glow plus a short trailing gradient. The head is clamped to the fill, and nothing animates on its own: no pulse, no travelling sheen, no particles.

### 14.3 Queue size restoration (WP3)

- `DownloadJob` persists `downloadedBytes`, `totalBytes`, and `totalIsExact` through `JobStore`, so sizes survive relaunch, service recreation and history reload.

- The recovery-attempt branch (impersonation flag, forced UA/referer) was removed from `DownloadRequestFactory`.
- `SingleAttemptPolicyTest`, `JobStateGuardTest`, and updated `DownloadRequestFactoryTest` pin the behaviour.

### 14.11 Live Alerts: Outcome B — the feature was removed

Reported symptom: the download notification showed a moving glyph under the progress bar and the
system never displayed a promoted Live Alert, while Settings offered a Live Updates entry.

The earlier correction attempted to satisfy the platform contract on both Android 16.0 and 16 QPR1
semantics (runtime probe of `hasPromotableCharacteristics()`, request extra, conditional colorizing,
a transparent tracker icon, and a gated Settings row). The structural contract was satisfied on the
API 36.0 emulator and the tracker glyph disappeared, but the promoted state itself was never
observed: that image cannot grant promotion to any third-party app
(`canPostPromotedNotifications() == false`, no `POST_PROMOTED_NOTIFICATIONS` in `framework-res`),
and no physical Android device was ever attached. `adb devices -l` listed only `emulator-5554`
during the final package.

The v5.1.0 stabilization package is explicit about this case: if the physical device cannot be
tested through ADB, do not claim successful promotion and implement Outcome B instead of keeping an
unverified feature. Outcome B was therefore applied:

- Removed the `Notification.ProgressStyle` construction, the promotion probe, the

### 15.1 Completion notification (P1) — root cause and correction

**Root cause (source inspection).** A job reaching `DONE` was handled as "no foreground work":
the foreground service and the transfer job both cancelled every per-job notification id. The
pipeline therefore never had a moment at which a completion record existed; the notification
disappeared exactly when the transfer ended.

**Correction.**

- A finished job posts a separate, dismissible, non-ongoing record on its own channel
  (`vrka_downloads_complete`, `IMPORTANCE_DEFAULT`, badges on), addressed by tag
  (`completed:<jobId>`, id `100100`) so neither idle-cleanup path can cancel it.
- The record reports the size of the **published document**, read back from the content
  provider, never the pre-merge estimate.
- Tapping it opens the published content URI with the provider's MIME type and a read grant;
  a visible **Open** action does the same.
- The platform drops notifications enqueued with a backdated timestamp, so the record uses the
  posting time.
- Posting is guarded by `state == DONE`, a non-empty output list and the notification
  permission; failures, cancellations and retries cannot post a completion. Without the
  permission the job still appears in History and no prompt is shown.

**Verification.** `CompletionNotificationTest` (7 instrumentation tests, API 36 emulator) covers
one dismissible record per job, the published-size text, no completion for failed/cancelled
jobs, survival of notification cleanup, distinct records for concurrent completions, the
content-URI/MIME open action, and the announcing/badged channel. The record itself was also
photographed on the emulator (§15.10, screenshot 5). *Not verified:* a completion produced by a
real transfer, because no production transfer can run on the x86_64 image (§15.10).

### 15.2 Estimated versus actual size (P2) — root cause and architecture

**Root cause (source inspection).** The queue treated every byte total as a single number per
job. A merged preflight estimate (video + audio) leaked into the completed row, and the progress
total could shrink back to the size of whichever stream was currently transferring. That is why a
finished item could display a number that never matched the file that was saved.

**Architecture.** Sizes now have three persisted sources that are never mixed
(`DownloadSize.kt`, `DownloadModels.kt`, `JobStore.kt`):

| Source | Meaning | Used by |
|---|---|---|
| Estimated | metadata preflight (`SizeEstimate`) — exact single stream, approximate merged/trimmed/re-encoded, or unavailable | Share card and pre-download confirmation |
| Reported | the active transfer's own total (`Downloaded x / y`), possibly approximate | Active queue and strip while transferring |
| Published | `DocumentFile` size after the file is written | Completed queue row, history and the completion notification |

A merged-stream tracker sums the separate video and audio totals without double counting and
without shrinking when one stream finishes. `DownloadSizeTest`, `DownloadSizeLabelTest` and
`JobStorePersistenceTest` pin the three sources, their labels and their persistence across
relaunch and service recreation.

**Not verified at runtime.** An estimate needs a live metadata probe, and a published size needs
a real transfer; neither runs on the x86_64 emulator (§15.10). The behaviour above is covered by
unit tests and source inspection only.

**Superseded by §16.2.** The three-source model is unchanged, but the estimated source now comes
from one complete metadata document per URL instead of one preflight per selected format.

### 15.3 First-install component versions (P3) — root cause and correction

**Root cause (reproduced on the API 36 emulator).** Two independent failures made a fresh
install read "Installed: Unavailable":

1. The yt-dlp artifact is a self-executing zipapp: a `#!` launcher line precedes the zip data.
   Android's `ZipFile` rejects that prefix ("invalid LFH signature") and `ZipInputStream` expects
   a local header at offset zero, so both bundled and installed reads failed.
2. The previous stream helper staged the archive through `java.io.tmpdir`, which is not
   writable by an app process.

**Correction.** `InstalledComponentVersionReader` skips the launcher preamble, unreads the bytes
from the real local header and parses the archive in place (bundled raw resource and installed
file use the same path). `ComponentVersionPriority` resolves metadata first — installed
artifact, bundled artifact, active runtime record, bounded `--version`, then caches — so a fresh
install reports the shipped yt-dlp and uBlock versions instead of "Unavailable".
`ComponentUpdateManager` publishes that value on construction.

**Follow-up correction in this pass.** The Settings "Stock yt-dlp" row did not use that reader:
`YtDlpRuntimeManager.stockVersion()` only executed the binary, so on the emulator — where the
ARM64 binary cannot run — the same screen showed `v2026.08.19` in the Components card and
`Installed: Unavailable` in the runtime card. `stockVersion()` now falls back
`--version` → installed artifact → bundled metadata, and caches the result against the binary's
size and modification time so a component update re-reads it while recomposition stays off disk.
`ComponentFirstInstallVersionTest` gains a test that the runtime card reports the shipped version
without executing the binary (5/5 tests pass on the emulator).

**Layout.** The Components card moves its badge and action under the version text below 320 dp of
card width, where German labels ("Update verfügbar" next to "Jetzt aktualisieren") previously
clipped. `ComponentCardNarrowScreenTest` renders the 288 dp case.

**Emulator evidence.** `qa/p10_first_install_versions.png` (fresh install: yt-dlp
`Installed: v2026.08.19`, uBlock `Installed: v1.74.0` next to available `v1.75.0`, "Not checked")
and `qa/p10_settings_components.png` (runtime card now `yt-dlp 2026.08.19`, `Active`, with the

### 15.5 Navbar rendering (P5)

**Root cause (source inspection of the vendored backdrop).** The bar read the pager offset, the
press flag and the press animation progress in composition; every swipe and press frame rebuilt
the glass/lens `drawBackdrop` elements, and because `ShapeProvider` has no `equals`, the vendored
`DrawBackdropElement.update` treated freshly allocated lambdas as a changed capture and re-ran

**Correction.** Pager position arrives through a `snapshotFlow`; the press animation starts from
the gesture; lens bounds are resolved in `Modifier.layout`; animated values are read at draw time
from remembered lambdas; the bar's draw modifier, ambient shadow and glass scale layer are
remembered. Geometry, colours, icons, labels, glass, refraction, lens and press effects are
unchanged.

`V5.1.0_DOWNLOAD_AND_NAVBAR_HARDENING.md` §8.6. Janky-frame ranges overlap (45.8–47.8% before,

### 16.2 Single-pass metadata extraction (WP2) — `a7d0e43`

**Root cause (source inspection).** The preflight passed the selected `-f` selector, so the
document described only one stream choice. Changing quality, audio mode or checking the share
card launched another process; the card and the main screen had no shared store, so the same URL
could be extracted twice. Size calculation also read only the shapes that matched the probe.
The stock runtime version was resolved by executing the ARM64 binary before the first preflight,
which added a CPython start-up on device and failed outright on the x86_64 emulator.

**Correction.**

- `DownloadRequestFactory.sizeEstimate` deliberately **omits `-f`** and uses
  `--simulate --dump-single-json --socket-timeout 10 --retries 2 --extractor-retries 1
  --no-playlist`. One invocation returns every video, audio and subtitle stream. The caller's
  25 s ceiling is unchanged; the socket and retry bounds fail a stalled request with a useful
  state instead of relying on a larger timeout.

### 17.2 Component update state stabilization (WP2) — `49f3726`

**Root causes (source inspection).** Four independent races and conflations produced a
persistent "Checking" card:

1. `isChecking` was true when either the discovery `checkState` or the installed-version
   `lifecycleState` was `CHECKING`. Resolving the installed version is a local read, so a slow
   artifact read kept the card and the Check All button in a checking state after discovery had
   already finished.
2. `_components` was published with a read-copy-write, so concurrent discovery, version
   resolution and worker observation could overwrite each other.
3. A superseded check could clear the `CHECKING` state belonging to a newer request.
4. A new discovery did not clear a previous terminal `UPDATE_SUCCESS`/`UPDATE_FAILED`, so a
   successful recheck could keep showing "Failed" or "Updated".

**Correction.** Installed-version resolution now has its own display-only
`isResolvingInstalledVersion` flag and never touches `checkState`; `isChecking` is derived only
from discovery, and `isUpdating` only from active update states. State publication uses
`MutableStateFlow.update` (atomic compare-and-set). A generation token records which request
owns `CHECKING`, and only that owner may clear it; superseded coroutines also `ensureActive()`.
`beginCheck` resets terminal install results to `UPDATE_IDLE`.

**Verification.** `ComponentUpdaterStabilityTest` (new, 171 lines) exercises the transitions,
ownership and resolution separation. On the emulator the startup check and a manual Check All
completed without a stuck state: `qa/wp8/ui/qa_02_settings_components.png`,
`qa/wp8/ui/qa_04_check_all.png`, and the updater log shows the check resolving cached releases
(`VRKA-ComponentUpdater: Using cached release for …`) with the card returning to
`Update available`.

### 17.7 ColorOS 17 trailing light wake (WP7) — `ff41bef`

allocation, blur filter or offscreen layer.
